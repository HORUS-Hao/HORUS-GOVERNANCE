## 總裁定

> **本任務僅解決 PIN 正確性是否可被自動判斷，**
> **不解決放行、不解決權限、不解決責任歸屬。**

---

## 一、問題 1：為何只自動化 pin_tmp / pin_hash 不會降低安全性

### 1.1 自動化範圍界定

| 項目 | 自動化 | 人工 |
|------|--------|------|
| hash 比對 | ✅ | - |
| 失敗次數計數 | ✅ | - |
| 帳號鎖定觸發 | ✅ | - |
| PIN 變更偵測 | ✅ | - |
| PIN 初始設定 | - | ✅ |
| PIN 交付 | - | ✅ |
| 帳號解鎖 | - | ✅ |
| 權限授予 | - | ✅ |

### 1.2 不降低安全性的原因

| 原因 | 說明 |
|------|------|
| **不觸碰明文** | 自動化僅比對 hash，不處理明文 PIN |
| **不改變驗證標準** | hash 比對邏輯與現有完全相同 |
| **不繞過防護** | 失敗鎖定機制仍然生效 |
| **不擴大攻擊面** | 無新增任何 API 或入口點 |
| **不改變儲存方式** | pin_hash 儲存方式不變 |

### 1.3 安全性維持證明

```
現有流程：
User → 輸入 PIN → sha256_(PIN) → 比對 pin_hash → 結果

自動化後：
User → 輸入 PIN → sha256_(PIN) → 比對 pin_hash → 結果
                    ↑                    ↑
                 無變更               無變更
```

| 安全控制點 | 現有 | 自動化後 | 變化 |
|------------|------|----------|------|
| PIN 最小長度 | 有 | 有 | 無 |
| 失敗鎖定 | 有 | 有 | 無 |
| OTP 二次驗證 | 有 | 有 | 無 |
| Session 過期 | 有 | 有 | 無 |
| hash 加密 | SHA-256 | SHA-256 | 無 |

## 二、問題 2：若 PIN 被濫用，最壞情境是什麼

### 2.1 濫用場景分析

| 場景 | 前提條件 | 可能性 |
|------|----------|--------|
| **PIN 外洩** | 明文 PIN 被第三方取得 | 低（人工交付） |
| **hash 外洩** | pin_hash 被第三方取得 | 低（Sheet 權限控制） |
| **暴力破解** | 攻擊者嘗試窮舉 | 極低（失敗鎖定） |
| **Session 劫持** | token 被第三方取得 | 低（token 過期機制） |

### 2.2 最壞情境描述

**假設：攻擊者取得有效 PIN + Email**

| 步驟 | 攻擊者行為 | 系統防護 | 結果 |
|------|------------|----------|------|
| 1 | 輸入 Email + PIN | PIN 驗證通過 | ✅ 通過 |
| 2 | 嘗試登入新裝置 | 觸發 OTP 驗證 | ⛔ 阻擋 |
| 3 | 無法取得 OTP | 無法完成登入 | ⛔ 失敗 |

**最壞情境（假設 OTP 也被取得）：**

| 步驟 | 攻擊者行為 | 後果 |
|------|------------|------|
| 1 | 完成登入 | 取得 Session |
| 2 | 嘗試操作 | **受限於 Role 權限** |
| 3 | VIEWER 角色 | ❌ 無法建立/核准報價 |
| 4 | CREATOR 角色 | ⚠️ 可建立報價（需核准） |
| 5 | APPROVER 角色 | ⚠️ 可核准（最大風險） |

### 2.3 風險邊界

| 風險 | 是否因 PIN 自動驗證增加 |
|------|-------------------------|
| PIN 被猜測 | ❌ 否（鎖定機制不變） |
| PIN 被竊取 | ❌ 否（交付方式不變） |
| 權限被提升 | ❌ 否（Role 系統獨立） |
| 流程被繞過 | ❌ 否（Approval 不變） |

### 2.4 最壞情境總結

> **最壞情境**：攻擊者同時取得 PIN + OTP + 高權限帳號 Email，可執行該帳號權限內的所有操作。
>
> **但這與 PIN 自動驗證無關**：此風險在自動化前後完全相同，因為自動化僅影響 hash 比對速度，不影響安全機制。

## 三、問題 3：為何這仍符合「非自動放行」

### 3.1 「自動放行」的定義

| 項目 | 定義 |
|------|------|
| 自動放行 | 系統自動決定是否允許執行某項操作 |
| 涉及範圍 | 狀態轉換、權限授予、核准動作 |

### 3.2 PIN 自動驗證 ≠ 自動放行

| 行為 | PIN 自動驗證 | 自動放行 |
|------|-------------|----------|
| hash 比對 | ✅ 做這個 | - |
| 決定登入成功 | ✅ 做這個 | - |
| 決定可建立報價 | - | ✅ 這才是 |
| 決定可核准報價 | - | ✅ 這才是 |
| 決定狀態轉換 | - | ✅ 這才是 |

### 3.3 層級分離

```
┌────────────────────────────────────────────┐
│           自動放行（禁止）                  │
│  - 自動核准報價                            │
│  - 自動狀態轉換                            │
│  - 自動權限提升                            │
└────────────────────────────────────────────┘
                    ↑
                    │ 完全獨立
                    ↓
┌────────────────────────────────────────────┐
│          PIN 自動驗證（本任務）             │
│  - hash 比對                               │
│  - 失敗計數                                │
│  - 結果回傳（true/false）                  │
└────────────────────────────────────────────┘
```

### 3.4 符合「非自動放行」的證明

| 檢查項目 | 結果 |
|----------|------|
| PIN 驗證後是否自動建立報價？ | ❌ 否 |
| PIN 驗證後是否自動核准報價？ | ❌ 否 |
| PIN 驗證後是否自動變更狀態？ | ❌ 否 |
| PIN 驗證後是否自動提升權限？ | ❌ 否 |
| PIN 驗證後是否自動發送郵件？ | ❌ 否 |

### 3.5 結論

> **PIN 自動驗證僅回傳「是/否」結果。**
> **後續動作（放行與否）仍由：**
> - **Role 權限系統決定**
> - **State Machine 狀態機決定**
> - **Approval Flow 審批流程決定**
>
> **因此，本任務完全符合「非自動放行」原則。**
