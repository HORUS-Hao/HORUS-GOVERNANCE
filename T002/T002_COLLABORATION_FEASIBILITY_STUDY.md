## 三、T002 欄位責任分類建議表

### 3.1 分類原則

| 分類 | 定義 | 特徵 |
|------|------|------|
| **System-Owned** | 系統自動產生/維護 | 人不應手動編輯 |
| **AI-Generated** | AI 清洗產出 | 人可覆寫但需記錄 |
| **Human-Input** | 人工輸入欄位 | 需要變更追蹤 |
| **Sync-Derived** | 從其他系統同步 | 唯讀，不可本地修改 |

| 欄位 | 責任分類 | 可編輯者 | 協作風險 | 備註 |

## 四、T002_CHANGE_LOG 欄位結構設計

### 4.1 設計目標

- 追蹤所有人工編輯行為
- 支援多人協作衝突檢測
- 提供稽核軌跡（Audit Trail）
- 支援還原（Rollback）需求

### 4.2 建議欄位結構

| # | 欄位名稱 | 資料類型 | 說明 | 範例 |
|---|----------|----------|------|------|
| 1 | log_id | Text | 變更記錄唯一 ID | `LOG_20260113_001` |
| 2 | timestamp | DateTime | 變更時間（ISO 8601） | `2026-01-13T14:30:00+08:00` |
| 3 | t002_id | Text | 被修改的 T002 記錄 ID | `T002_20250812_002` |
| 4 | field_name | Text | 被修改的欄位名稱 | `標準化品牌` |
| 5 | old_value | Text | 修改前的值 | `삼성전자` |
| 6 | new_value | Text | 修改後的值 | `SAMSUNG` |
| 7 | editor_email | Text | 編輯者 Email | `user@horus.tw` |
| 8 | edit_source | Enum | 編輯來源 | `SHEET_ADDON` / `WEB_UI` / `API` |
| 9 | edit_reason | Text | 編輯原因（選填） | `韓文品牌名稱標準化` |
| 10 | session_id | Text | 編輯 Session ID（可選） | `sess_abc123` |

### 4.3 範例資料

```
log_id              | timestamp                    | t002_id           | field_name   | old_value  | new_value | editor_email       | edit_source  | edit_reason
--------------------|------------------------------|-------------------|--------------|------------|-----------|--------------------|--------------|-----------------
LOG_20260113_001    | 2026-01-13T14:30:00+08:00   | T002_20250812_002 | 標準化品牌   | 삼성전자   | SAMSUNG   | user@horus.tw      | SHEET_ADDON  | 韓文標準化
LOG_20260113_002    | 2026-01-13T14:31:00+08:00   | T002_20250812_002 | AI清洗狀態   | 需人工確認 | 清洗完成  | user@horus.tw      | SHEET_ADDON  | 人工確認完成
LOG_20260113_003    | 2026-01-13T14:32:00+08:00   | T002_20250812_002 | 人工確認人   |            | user@horus.tw | user@horus.tw | SHEET_ADDON  |
```

## 五、實作管道分類

### 5.1 適合 Sheet Add-on 的功能

| 功能 | 理由 | 優先級 |
|------|------|--------|
| **人工確認流程** | 直接在 Sheet 內操作，低學習成本 | P0 |
| **標準化欄位覆寫** | 就地編輯，搭配 Change Log 記錄 | P0 |
| **備註填寫** | 簡單文字輸入，無需複雜 UI | P1 |
| **狀態標記** | 下拉選單操作，符合 Sheet 原生體驗 | P1 |
| **Change Log 檢視** | 側邊欄顯示該列的變更歷史 | P1 |
| **衝突警示** | 偵測同一欄位近期被他人修改 | P2 |

### 5.2 適合未來 Web UI 的功能

| 功能 | 理由 | 階段 |
|------|------|------|
| **批量確認介面** | 需要跨列操作，Sheet 不適合 | Phase 2+ |
| **AI 清洗規則管理** | 需要複雜配置介面 | Phase 2+ |
| **T005 轉換預覽** | 需要並排比對顯示 | Phase 2+ |
| **稽核報表** | 需要圖表與統計功能 | Phase 2+ |
| **供應商資料批量匯入** | 需要檔案上傳與進度追蹤 | Phase 3+ |
| **權限管理介面** | 需要完整的 RBAC UI | Phase 3+ |

### 5.3 管道選擇決策樹

```
需要編輯的欄位？
├─ 是 → 是否為單列操作？
│       ├─ 是 → Sheet Add-on ✅
│       └─ 否（批量）→ Web UI
└─ 否（唯讀檢視）
        ├─ 需要圖表/報表？→ Web UI
        └─ 只看變更歷史？→ Sheet Add-on 側邊欄 ✅
```

## 六、Phase 1 試行建議

### 6.1 建議範圍

| 項目 | 內容 | 風險 |
|------|------|------|
| **目標欄位** | 標準化品牌、標準化型號、標準化名稱、備註 | 可控 |
| **目標功能** | 人工確認 + Change Log 記錄 | 可控 |
| **實作方式** | Google Sheets Add-on（Apps Script） | 低 |
| **使用者** | 1-2 位內部測試者 | 低 |
| **資料量** | 10-50 筆測試記錄 | 低 |

### 6.2 Phase 1 不包含

- ❌ T005 自動同步
- ❌ AI 清洗引擎整合
- ❌ 批量操作
- ❌ 外部使用者

### 6.3 成功指標

| 指標 | 目標值 |
|------|--------|
| Change Log 記錄完整率 | 100% |
| 編輯衝突發生率 | < 5% |
| 使用者操作錯誤率 | < 10% |

## 七、風險評估

### 7.1 最大風險點

#### 風險 1：治理衝突（嚴重度：高）

| 項目 | 說明 |
|------|------|
| 風險描述 | T002 目前處於 HOLD 狀態（ADR-0001），任何實作可能違反治理規則 |
| 影響範圍 | 整個 T002 協作功能開發 |
| 緩解措施 | Phase 1 試行前須取得 Architect 明確批准，並更新 ADR 狀態 |
| 建議行動 | 先完成 ADR 變更審批，再啟動技術實作 |

#### 風險 2：T005 同步干擾（嚴重度：中高）

| 項目 | 說明 |
|------|------|
| 風險描述 | T002 變更可能影響 T005 轉入流程，造成資料不一致 |
| 影響範圍 | T002 → T005 資料流 |
| 緩解措施 | Phase 1 僅允許「尚未轉入 T005」的記錄進行人工編輯 |
| 建議行動 | 在 Sheet Add-on 中加入「已轉入 T005」的編輯鎖定 |

### 7.2 次要風險

| 風險 | 嚴重度 | 緩解措施 |
|------|--------|----------|
| Sheet 性能問題（大量 Change Log） | 中 | 定期歸檔舊記錄 |
| 使用者誤操作 | 低 | 提供 Undo 機制 |
| Apps Script 配額限制 | 低 | 監控 API 使用量 |

## 八、結論與建議

### 8.1 Phase 1 試行可行性

| 評估項目 | 結論 |
|----------|------|
| 技術可行性 | ✅ 可行（Sheet Add-on 技術成熟） |
| 治理可行性 | ⚠️ 需先取得 ADR 變更批准 |
| 風險可控性 | ✅ 可控（限制範圍 + Change Log） |
| 資源需求 | ✅ 低（單人開發 1-2 週） |

### 8.2 建議下一步

1. **治理層**：向 Architect 提交 ADR 變更請求，將 T002 從 HOLD 調整為「Phase 1 試行」狀態
2. **技術層**：待 ADR 批准後，設計 Sheet Add-on 架構
3. **測試層**：建立獨立測試 Sheet，不影響現有資料

### 8.3 最終建議

> **建議：有條件地適合 Phase 1 試行**
>
> 前提條件：
> 1. ADR-0001 須更新為允許 Phase 1 試行
> 2. 試行範圍限於「尚未轉入 T005」的記錄
> 3. 必須實作 Change Log 機制
>
> 最大風險點：
> 1. 治理衝突（需 ADR 批准）
> 2. T005 同步干擾（需編輯鎖定機制）
